## 1. 项目是什么

柔性视觉供料系统的**上位机**（Qt Widgets 桌面程序），通过 **RS485 串口或 TCP(以太网)** 控制下位机完成三类动作：

1. **振动盘运动**：9 种动作（上/下/左/右/聚拢/水平居中/垂直居中/振散/翻面），由按钮参数（电压/频率/时间/角度偏移/速度系数）驱动；
2. **料仓运动**：电压/频率/时间三参数，语义与振动盘一致——**下位机运动完成后才回帧**；
3. **光源控制**：上位机和 RBT6 应用代码支持 A/B/C/D 四路光源（索引 1/2/3/4），各自有亮度(0~100)与保持时间，**开启后 1s 内必须收到下位机完成反馈**。C/D 使用 TIM1_CH1/CH4；旧 `FlexControlSTM32/` 本轮未同步，不能据代码推断板上已烧录。

三类动作的**时间**都可以设成"无限"（UI 上勾「保持」，协议里是数据域末字节 1），此时一直动作到收到停止指令为止，详见第 4 节「保持」标志位。

当前主用下位机固件已迁移到同仓库 **`FlexControlSTM32RBT6/`**（STM32F103RB，128KB Flash，HAL库，MDK-ARM工程），应用层在 `FlexControlSTM32RBT6/Application/`；原 `FlexControlSTM32/` 保留为旧平台。模块包括 FlexControl / MotorControl / BinControl / LightControl / LinkState / Network / SerialHandle / SaveParams / Timer / W5500。主循环 `FlexControlHandle()` 依次处理网络重试/收发、统一指令分发、串口状态机、链路超时、三个执行器和 LED；LED不新增中断，使用现有HAL毫秒节拍。本文旧路径与旧引脚说明保留为历史背景，RBT6 现状以末尾迁移日志为准。

### 下位机框架约定（仿 MotorControl 模式）

- **指令入口**：`SerialHandle.c::ParseUartData()` 按指令码识别帧（0x01/03/05/07/09/0B/0D），解析进 `SerialInfo`（共享环形缓冲 `SERIAL_INFO_BUFFER_SIZE=16`），`FlexControl.c::SerialRecvInfoHandle()` 按类型分发到对应模块。
- **模块模式**（MotorControl/BinControl/LightControl 三家一致）：环形队列暂存指令（`SendXxxInfo`/`Get`/`Clear`，队列长度：振动盘 16 / 料仓 4 / 光源 4）→ 主循环非阻塞处理（Motor/Bin 是 GET_INFO → Prepare（算查表参数）→ HANDLE 的 FSM；**Light 没有 FSM**，因为两路光源各自独立状态，改成"排空队列 + 逐路扫描"）→ 完成时调 `__weak` 回调（`CbXxxFinish`），回调在 `FlexControl.c` 实现 → `SendSerialRespond()` 发应答帧。
- **料仓查表驱动（已实装）**：料仓占用 **TIM3_CH1(PA6)=极性P / CH2(PA7)=极性N**，与振动盘单个执行器同一套双极性接法。查表与 MotorControl 共用同一张占空比正弦表 `g_s16DutyTable1Cycle[1600]`（定义在 MotorControl.c，USE_SIN_WAVE 分支，**幅值正好 ±4499 = ARR**）；`PrepareBinMotion` 用与 `PrepareMotion` 相同的公式算 `DutyZoom`/`Span`/`Index`（Q15）：`CCR = 表值 × DutyZoom >> 15`，正半周走 CH1、负半周走 CH2，`Span = 1600×32768 / (1/f/62.5µs)`（10Hz→每 PWM 走 1 个表点，200Hz→走 20 个）。表索引走满 1600 点**回绕继续振**（不像振动盘那样停），直到运动时长到。
- **`BinPwmPulseCallback()` 由 `MotorControl.c` 的 `HAL_TIM_PWM_PulseFinishedCallback()` 转发**：HAL 的脉冲完成回调只能有一处定义，那个回调是现有的总入口（先转发料仓、再遍历振动电机）。**TIM3 与光源共用**：光源 CH3/CH4 是纯电平输出、不开中断，所以不会进这个回调。
- **光源硬件映射**（TIM3 由 CubeMX 配好：PSC=0，ARR=4499，CH1~CH4 全为 PWM 输出、OCPolarity=HIGH）：
  - **光源A(LIGHT1) = TIM3_CH3 = PB0**，**光源B(LIGHT2) = TIM3_CH4 = PB1**；
  - 亮度 0~100 线性折算：`CCR = 亮度 × (ARR+1) / 100 = 亮度 × 45`（0→0 恒低熄灭，100→4500>ARR 恒高满占空比）；
  - **两路完全独立**：各有 `bOn / u8Brightness / u16KeepTime / u32TimerCount`，开关与保持时间计时互不影响；
  - **铁律：不能用 `HAL_TIM_PWM_Stop()` 关灯**——它会 `__HAL_TIM_DISABLE` 整个 TIM3 计数器，而 CH1/CH2 是料仓在用的，会把料仓 PWM 一起停掉。关灯只把该路 CCR 写 0；通道在 `LightControlInit()` 里 `HAL_TIM_PWM_Start` 一次，之后不再启停。
- **光源时序**：点亮成功（CCR 已写入）立即回 0x0C（满足上位机 1s 时限），保持时间（单位 100ms）到自动熄灭并回 0x0E；**保持时间 0 = 常亮**，不自动熄灭。上位机主动关（0x0D）走 `LightControlStop(u8Index)`：索引 1/2 只关该路、0 关全部，并丢弃队列中该路排队中的开启指令（否则关完又被点亮）；未点亮时也回 0x0E。
- **新增下位机指令的 checklist**：SerialHandle.h 扩 `InfoType/RespondType`（必要时扩 `SerialInfo`）→ ParseUartData 加 case + Parse 函数 → SendSerialRespond 加应答（用 `SaveRespondFrame()` 通用组帧）→ 新建/扩展模块（队列+FSM+weak 回调）→ FlexControl.c 接分发/回调/Init/Handle → uvprojx 加文件 → 上下位机联调对帧。

## 2. 源码结构与职责

| 文件 | 职责 |
|---|---|
| `ProtocolHandle.h` | 协议抽象基类（QObject）。定义 `GeneralMotion::MotionParams`（运动索引枚举含 `MotionBin`）+ 各指令的组帧虚函数。新增指令先在这里加虚函数（给默认空实现即可） |
| `generalprotocol.h/.cpp` | 唯一实现类 `GeneralProtocol`（单例）。帧头尾常量、指令码常量、`AddCheckSum`、各协议的"发送帧 + 期望应答帧"成对生成 |
| `ConnectiveHandle.h/.cpp` | **通信引擎**（与传输方式无关）：按指令类型分队列、10ms 引擎 tick（发送队首/等应答/判超时）、1s 心跳、接收帧状态机、应答精确匹配 |
| `rs485handle.cpp/h`、`tcphandle.cpp/h` | 传输层子类：只实现 `OpenChannel/CloseChannel/WriteData` 三件套，收到原始字节调 `FeedReceivedBytes()` |

| `style/app.qss` + `style/app.qrc` | **全局视觉样式（唯一出口）**，编译进 qrc 由 `main.cpp` 加载。见下方「视觉主题」小节 |

### 视觉主题（`style/app.qss`，2026-11-24 引入「B 浅色卡片」）

- **唯一出口**：除"随数据变化的颜色"外，**不要在 cpp 里再写 `setStyleSheet`**。当前全工程只剩 `ControlPanel::SetKeyParamsStatus()` 一处（固件参数状态行的红/灰切换，样式表无法按状态切色）。样式表通过 `FlexControlSystem.pro` 的 `RESOURCES += style/app.qrc` 编译进 exe，**不依赖外部 qss 文件**——拷 exe 到现场不会漏带文件而退回原生老界面。

## 3. 线程模型（重要，改动时别破坏）

- `ConnectiveHandle`（及其 RS485/TCP 子类）被 `moveToThread` 到独立工作线程；所有队列、定时器、串口/socket 操作都在该线程内，无跨线程数据访问。
- UI 与引擎之间全部走 Qt 信号槽（跨线程自动排队连接）。
- 断开流程 `CloseConnection()`：**开头统一 `ui->ControlTabWidget->setEnabled(false)`**（2026-11-02 加，2026-11-25 九次改锚点：原来禁的是外层 `tabControl`，该容器已被 Designer 合并），覆盖所有断连路径（心跳丢失/主动断开 TCP/485/连接失败/析构）；然后 `disconnect()` 全部信号 → `QThread::finished` 直连 `Shutdown()`（在工作线程内停定时器/关串口）→ quit/wait → 直接 delete（不用 deleteLater，避免事件循环先退出导致泄漏）。
- `ui->ControlTabWidget` 的启用/禁用约定：初始禁用（构造函数）→ 连接成功 `OnConnectiveState(true)` 时启用 → 任何路径走 `CloseConnection()` 时禁用。断连后 `sigMotionTerminate` 恢复 lambda 仍会把 ControlPanel 按钮 `setEnabled(true)`，但因父容器 `ControlTabWidget` 禁用，按钮不可点（Qt 行为：父容器禁用时子控件即便 enabled 也不可交互）；下次连接成功时它重新启用，按钮立即可点。**2026-11-23 追加**：`CloseConnection()` 开头还调 `m_pControlWidget->ResetMotionUiState()`——断连时 `m_ConnectiveHandler->disconnect()` 会把所有信号掐掉，在飞的指令不会再有完成帧，若不复位，运动锁（见第 6 节）会一直挂着，重连后运动类型按钮永久置灰。

## 4. 通信协议速查（帧格式：55 AA | 指令 | 长度 | 数据 | 校验2B | AA 55）

校验 = 指令起所有字节累加后**取反加一**（16 位，高字节在前）。数据域为空时按公式算出来自然是 0x00 0x00 之外的 0xFFxx——注意 docx 里"长度为 0 时校验为 0"的说法与心跳示例(FF FF)矛盾，**实现以示例为准**（两字节补码），上位机/下位机两端必须一致。

| 指令 | 码 | 长度 | 数据域 | 应答 | 超时策略 |
|---|---|---|---|---|---|
| 心跳 | 01 | 0 | 无 | 02 | 1s，**超时视为断连**，清队列+关连接 |
| 振动盘运动 | 03 | **14**(十进制) | 索引1B+电压×10 2B+频率×10 2B+时间s×10 **4B**+角度偏移2B+速度系数2B+**保持标志1B** | 04(索引+0x01) | 计时动作：**时间×100ms + 2000ms 冗余**；保持=1：**24h 兜底**（运动完成才回） |
| 振动盘停止 | 05 | 0 | 无 | 06 | 1s；入队时清空运动队列并发 terminate |
| 料仓运动 | 07 | **10** | 索引1B(固定0x01)+电压×10 2B+频率×10 2B+时间s×10 **4B**+**保持标志1B** | 08(索引+0x01) | 同振动盘（`[9]`~`[12]` 仍是时间域；保持=1 走 24h 兜底） |
| 料仓停止 | 09 | 0 | 无 | 0A | 1s；入队时清空料仓运动队列并发 terminate |
| 开光源 | 0B | **7** | 索引1B(1=A,2=B,3=C,4=D)+亮度1B(0~100)+保持时间s×10 **4B**+**保持标志1B** | 0C(仅索引1B) | **1s**（要求开启后 1s 内收到完成反馈） |
| 关光源 | 0D | 0 或 1 | 无（N=0，关全部）/ 索引1B（N=1，只关指定路，**沿用已有协议扩展**） | 0E（**保持时间到时自发该帧并带索引**；手动停止应答无索引；A/B/C/D 由索引区分） | 1s |
| 获取电压 | 13 | 1 | 固定 0x01 | 14（2B 电压×10 大端） | 2s（**上位机连接后每 2s 自动轮询**，超时静默重发） |
| 获取固件参数 | 15 | 1 | 固定 0x01 | 16（**状态 1B + 12×float 4B 大端 = 49**） | 2s（`GET_KEY_PARAMS_TIMEOUT_MS`） |
| 保存固件参数 | 17 | **49** | 标志 1B（固定 0x01）+ 12×float 4B 大端 | 18（结果 1B：**0 = 成功 / 1 = 失败**） | 3s（`SAVE_KEY_PARAMS_TIMEOUT_MS`，要等 Flash 擦写完） |
| 获取固件版本 | 19 | 1 | 固定 0x01 | 1A（**3B：major / minor / patch**） | 2s（`GET_FW_VERSION_TIMEOUT_MS`；**连接后读一次**，超时静默显示 `--`） |

多字节整数均为**大端**。所有数值字段都 ×10 后取整发送（电压/频率/时间/速度）。

> **时间域 2 字节 → 4 字节（2026-11-25 十九次，0x03 / 0x07 / 0x0B 三条指令）**
> - 位置：都是"数据域第 6~9 字节"（振动盘/料仓在整帧下标 9~12；光源在第 3~6 字节）。**保持标志仍是数据域最后一个字节**，不用改定位方式（按长度域算）。
> - 量程：0~9999 s，×10 后最大 **99990**，`uint16`(65535) 装不下 —— 这就是必须改宽度的原因，**只放大界面 spinbox 会把 6553.5s 以上的时长回绕成小值**。
> - 上位机：`generalprotocol.cpp` 的 `AppendUInt32BigEndian()` + `TimeToTicks()`（0.1s 刻度**四舍五入**，`0.8f` 截断会变 0.7）；超时估算在 `ConnectiveHandle.cpp` 的 `ReadTimeTicks()/MotionTimeoutMs()`。
> - **下位机（`FlexControlSTM32RBT6` 已改，2026-11-25）**：① 解析函数 `SerialHandle.c::ParseMotionData/ParseLightData`（串口，环形缓冲按 `u16DataIndex+偏移` 取字节）与 `ParseNetworkMotionData/ParseNetworkLightData`（网络，`pFrame[n]`）改成 4 字节大端；② `SerialInfo.u16LightKeepTime` → **`u32LightKeepTime`**，`LightParams.u16KeepTime` → **`u32KeepTime`**、`LightChannelState.u16KeepTime` → **`u32KeepTime`**、`LightTurnOn()` 形参同步；③ 运动/料仓的 `fMotionTimeUse` 本来就是 `float` 秒、下游 `u32TimeUseExpect = fTimeUse*1000` 与 `u32TimeUseMs` 也都是 **uint32**，所以这两条只改解析偏移，计时链路无需再动。
>   - **串口侧偏移一览（`u16DataIndex` = 命令字下标）**：运动 = `+2` 索引、`+3~4` 电压、`+5~6` 频率、**`+7~10` 时间**、`+11~12` 角度、`+13~14` 系数、末尾标志按长度域定位；光源 = `+2` 索引、`+3` 亮度、**`+4~7` 保持时间**、末尾标志。
>   - **光源到点判据**：`GetTimerTickDelta(...) >= u32KeepTime * 100`（tick = 1ms，9999s → 9 999 000ms，`uint32` 放得下，`Timer.c::GetTimerTickDelta` 自带回绕处理）。
>   - **另一套 `FlexControlSTM32`（标准版）未改**：那份代码停在 2026-11-11，连 2026-11-22 的「保持」扩展（`u8InfiniteTime`）都没有，属于旧分支，要启用得先把中间几轮协议扩展一起补上。
> - 帧校验/应答帧**完全不变**（应答 0x04/0x08/0x0C 没有时间字段），只改下发帧。
> - 核对工具：`build-check/test_time9999.cpp`（上位机组帧：帧长/长度域/时间刻度/角度/系数/标志位 + 独立复算校验和，20 项全 PASS）；`build-check/test_fw_parse.c`（**把上位机实发帧喂给固件侧的同一套下标表达式**，验证解码回 9999.0s / 99990 格、0.8s 不丢精度、-22 系数符号正确，17 项全 PASS）。实测帧：`55 aa 03 0e 01 0064 03e8 00018696 0000 0000 00 fd82 aa55`（9999s → `00 01 86 96`）；光源 `55 aa 0b 07 01 64 00018696 00 fe6c aa55`。

### 固件版本（0x19 / 0x1A，2026-11-25 二十二次；协议文档第 10 节）

| 方向 | 帧 | 说明 |
|---|---|---|
| 上位机下发 | `55 AA 19 01 01 FF E5 AA 55` | 数据域 1 字节，固定 `0x01`；整帧 **9 字节** |
| 下位机反馈 | `55 AA 1A 03 00 01 00 FF E2 AA 55` | 数据域 3 字节 = `major / minor / patch`；整帧 **11 字节** |

- **只读一次，不轮询**：`ControlWidget::OnConnectiveState(true)` 里在启动电压轮询之后投递一次 `SendGetFirmwareVersionCommand`（`QMetaObject::invokeMethod` + `QueuedConnection`，与电压查询同一条路径）。固件不换，版本不会变；重连会再读一次。
- **超时静默**：`GET_FW_VERSION_TIMEOUT_MS = 2000`，超时清队列并 emit **空串**，标签显示 `--`。旧固件没实现 0x19 时就是这样，**不要改成弹框**——现场因为读不到版本号弹窗是纯打扰。
- **应答不预构造期望帧**：和 0x16/0x18 一样，`RecvMessageHandle()` 按"命令码 `at(2) == 0x1A` + 长度 `at(3) == 3`"匹配，再取 `at(4..6)`。**同理不校验校验和**（见第 9 节"只按命令码匹配"那条）。
- **上位机链路**：`GeneralProtocol::GetFirmwareVersionProtocol()` 组帧 → `ConnectiveHandle::SendGetFirmwareVersionCommand()` 入队/超时 → `sigGetFirmwareVersionResult(QString)`（引擎已拼成 `"0.1.0"`）→ `ControlWidget::OnFirmwareVersionResult()` → `SetFirmwareVersion()`。
- **下位机**（`FlexControlSTM32RBT6`）：版本号唯一来源是 `Application/Version.h` 的三个宏 `FW_VERSION_MAJOR/MINOR/PATCH`（当前 0/1/0）；`FlexControl.c::GetFirmwareVersionHandler()` 只做"宏 → 3 字节 → `SendSerialRespond(RESPOND_GET_FW_VERSION, ...)`"的搬运，`SerialHandle.c` 串口与网络两条解析路径各加 `case 0x19`，应答走 `SaveRespondFrame(0x1A, pParams, 3)`。**改版本只改 Version.h**，不要在 handler 里写字面量。
- **核对工具**：`build-check/test_fw_version.c`（把两端校验和算法搬到一起对撞：请求帧 `55aa190101ffe5aa55`、应答帧 `55aa1a03000100ffe2aa55`、坏校验被丢、255.255.255 边界，14 项全 PASS）；`build-check/fwver_test/`（真实 `ConnectiveHandle` + 内存传输桩：未连接不发、帧字节、不堆叠、0x1A 解出 0.1.0、错长度/坏校验/自发帧不误触发、重连再读、2s 超时静默发空串，18 项全 PASS）。

### 固件参数（0x15~0x18，2026-11-23）

12 个 float，顺序固定（`GeneralKeyParams::KeyParams` / 下位机 `KeyParams` 两端必须一致）：`fUpStartPhaseLeading, fUpPhaseOffset, fDownStartPhaseLeading, fDownPhaseOffset, fLeftStartPhaseLeading, fLeftPhaseOffset, fRightStartPhaseLeading, fRightPhaseOffset, fHGatherStartPhaseLeading, fHGatherPhaseOffset, fVGatherStartPhaseLeading, fVGatherPhaseOffset`。共 **48 字节**；加状态/标志字节后数据域 49，整帧 **57 字节**。

- **float 一律 IEEE754 单精度 + 大端（网络字节序）**：上位机 `AppendFloatBigEndian()/ReadFloatBigEndian()`（`generalprotocol.cpp` 匿名命名空间），下位机 `PutFloatBigEndian()/GetFloatBigEndian()`（`KeyParameters.c`）。**不要用 `memcpy` 直接怼**——x86/ARM 都是小端，不转字节序两端必然对不上（1.375f = `3F B0 00 00`）。
- **0x16 的状态字节语义**：`0` = 本次是从 Flash 读出来的有效值；**非 0 = Flash 无效（擦除态/校验不过/版本不符），返回的是默认值**。注意下位机 `GetKeyParams()` 无论读成功失败**都会填好默认值并回当前值**，所以"状态=1"不代表数据不可用，只代表"这批是默认值还没保存过"。
- **⚠️ 0x18 的语义与「保存 IP」那条指令相反**：本条 **0 = 成功、1 = 失败**（沿用 `SaveParams` 的习惯）。上位机判断写在 `OnSaveKeyParamsResult()` 里，改之前先看一眼，别想当然按"0 失败"处理。
- 下位机存储：`KeyParameters.c`，Flash 页 **0x0800F800**（`SaveParams` 占 0x0800FC00，各占 1KB 页），结构 `magic(4) + version(2) + reserved(2) + 12×float(48) + checksum(2)`；三项校验（magic / version / checksum）全过才认 Flash 里的值。保存流程与 `SaveParams.c` 同构：解锁 → 擦页 → 半字编程 → 上锁 → **回读 memcmp 一致才返回成功**。
- **上电即加载，不等 0x15（2026-11-23 补）**：`FlexControlInit()` 里 `SaveParamsInit()` 之后紧跟一句 `GetKeyParams()`，把 Flash 里的相位参数填进全局 `g_sKeyParams`。理由：**上位机连上之前电机就可能收到运动指令**，若等到第一条 0x15 才填，`g_sKeyParams` 一直是 BSS 清零的**全 0 相位**（0 相位下电机抖动/不出力）。`GetKeyParams()` 只读 Flash 不写，失败也回默认值，不影响启动；之后每次收到 0x15 仍会重读一遍刷新（Flash 才是真相来源）。
- **`g_bKeyParamsFromFlash`（新增）**：上一次 `GetKeyParams()` 是否真从 Flash 取到有效值，纯诊断用。**Flash 里存的值可能碰巧等于默认值，光看 `g_sKeyParams` 的数值分不出"读到了"还是"回默认了"**，调试时看这个标志。每次 `GetKeyParams()` 开头先置 false，三项校验全过才置 true（**不能只在 return false 前清**，否则上一次成功的 true 会残留、谎报"值来自 Flash"）。
- **注意参数目前还没有消费方**：`g_sKeyParams` 现在只被 0x16 应答读取（`KeyParamsPack`），`MotorControl.c` 里各方向的起始相位仍是硬编码（`u32UpPhaseStart = 2200` / `u32DownPhaseStart = 2200` / `u32VGatherPhaseStart = 2200`）。换算关系：**一圈 1600 微步**（`% 1600`），故 `1.375 × 1600 = 2200` 正好对上默认值 `fUpStartPhaseLeading = 1.375`。要让参数生效需在 `MotorControl.c` 里改成 `(uint32_t)(g_sKeyParams.fUpStartPhaseLeading * 1600.0f)` 之类的取用；`fXxxPhaseOffset`（默认 0.4375 / 0.25 / 0.5）在电机代码里**暂时找不到对应消费点**，接之前先确认它的物理含义（两电机间相位差？）,别按微步直接乘 1600 猜。


### 「保持」标志位（2026-11-22 协议扩展，0x03 / 0x07 / 0x0B 三条指令数据域的**最后一个字节**）

- `1` = 无限时间动作 / 无限保持；`0` = 遵从同一帧前面设置的时间（与旧帧行为完全一致，老配置下发 0，等同未扩展）。
- 落到各指令上的字面含义：**振动盘 / 料仓 = 一直动作，直到收到停止指令（0x05 / 0x09）**；**光源 = 常亮，直到收到关灯指令（0x0D）**。
- **取该字节的方式（上下位机两侧一致）**：按长度域定位 `下标 = 指令字下标 + 1(长度字节) + 长度值`，即"数据域最后一个字节"。**不要从校验和往前倒着数**——虽然现在也是倒数第 3 字节，但一旦有人往后面加字段就会错位。下位机实现见 `SerialHandle.c::ParseMotionData()/ParseLightData()`（串口）与 `ParseNetworkMotionData()/ParseNetworkLightData()`（网络，用 `pFrame[1 + pFrame[1]]`）。
- 光源的"保持"**复用已有的"保持时间 0 = 常亮"语义**：`FlexControl.c::LightOnHandler()` 把标志折算成 `u16KeepTime = 0`，所以 `LightControl` 没有新增任何状态位（见第 1 节光源时序）。

### 超时常量位置
`ConnectiveHandle.cpp` 顶部宏：`ENGINE_TICK_MS=10`、`HEART_BEAT_PERIOD_MS=1000`、`HEART_BEAT_TIMEOUT_MS=1000`、`STOP_MOTION_TIMEOUT_MS=1000`、`BIN_STOP_TIMEOUT_MS=1000`、`LIGHT_RESPOND_TIMEOUT_MS=1000`、`RECV_PARSE_TIMEOUT_MS=2000`（接收半帧超时复位状态机）、`INFINITE_MOTION_TIMEOUT_MS = 24×3600×1000 = 86400000`（保持=1 时运动/料仓用这个兜底，见上表）、`GET_KEY_PARAMS_TIMEOUT_MS=2000`、`SAVE_KEY_PARAMS_TIMEOUT_MS=3000`（Flash 擦写比读慢，给 3s）、`GET_FW_VERSION_TIMEOUT_MS=2000`（连接后读一次，超时静默）。

## 5. 一条指令的完整生命周期（以料仓运动为例）

1. 用户点 `pbBinStartMotion` → `ControlPanel::on_pbBinStartMotion_clicked()`：从 `dspbBinVoltage/Frequency/Time` 取值 → `m_pProtocol->BinMotionProtocol()` 生成 (发送帧, 期望应答帧) → `emit sigBinMotion(...)` → 禁用开始、使能停止按钮；
2. `ControlWidget::SetConnectSlot()` 里预建的连接把信号投递到工作线程的 `ConnectiveHandle::SendBinMotionCommand()`：入 `SendCmdType::BinMotion` 队列，超时 = 帧[9][10]×100+2000；**若帧末「保持」字节为 1，改用 `INFINITE_MOTION_TIMEOUT_MS`（24h）**，见 4 节；
3. 10ms 引擎 `OnEngineTick()`：队首未发则 `WriteData()`（写失败下个 tick 重试）；已发则等 `bRespond` 或超时；
4. 下位机回帧 → 子类 readyRead → `FeedReceivedBytes()` 状态机组帧 → `RecvMessageHandle()` 与各队列队首的期望应答做**全帧字节精确比对** → 置 `bRespond=true`；
5. 下个 tick 引擎弹 出队首并 `emit sigMotionTerminate()` → ControlPanel 的 lambda 恢复全部按钮（振动盘/料仓/光源统一回到空闲态）；
6. 超时路径：`emit sigBinMotionRespondUnnormal()` → ControlWidget 弹"料仓反馈超时" → `OnConnectiveUnnormal()` 末尾统一 `emit m_pControlWidget->sigMotionTerminate()` 恢复按钮。

注意：**振动盘运动、料仓运动、光源开关是相互独立的队列，可同时在途**（光源与振动可并行）；同类型指令内部串行（队列 FIFO）。

## 6. UI 按钮互锁约定（ControlPanel）

- **所有按钮的 clicked 都必须手动 connect**（`setupUi(parent)` 使自动连接失效，详见第 9 节）。漏连 = 按钮可点但无任何反应。
- 构造函数里 `sigMotionTerminate` 的 lambda 是**唯一的统一恢复点**：恢复振动盘(发送/停止)、料仓(开始/停止)、光源 A/B/C/D(开/关) 全部按钮到空闲态。任何"完成/超时/停止/断连"最终都汇到这里。该 lambda **开头有 `if (!m_bRunEnabled) return;`**，防止把"未连接、本就不该可点"的面板按钮"恢复"成可点。

- **"能不能下发"只由链路决定（2026-11-25 二十次，重要）**：以前只有运行页那个面板能发指令，「配置数据」窗口里的 `m_pModeWidget` 是 `SetReadOnly(true)` 永久禁用；现在两个面板**都能发**，判据统一成 `m_bRunEnabled`：
  - `ControlPanel::SetRunEnabled(bool)` 是唯一开关：`true` → 刷成空闲态（发送可点/停止灰/9 个运动类型键全开/料仓可开不可停/四路光源可开不可关）；`false` → 14 个运行键全灰（`pbSendMotion/pbSendMotionStop/pbG1/pbG2` + 料仓 2 + 光源 8）。
  - 9 个**运动类型按钮不受 `SetRunEnabled(false)` 影响**：配置页要随时能点选切换"正在编辑哪一份参数"。
  - `ControlWidget` 在 `OnConnectiveState(true)` 里 `m_pModeWidget->SetRunEnabled(true)`，`CloseConnection()` 里 `ResetMotionUiState()` **之后**再 `SetRunEnabled(false)`（顺序反了的话"回空闲"会被自身判据挡掉，断连后状态灯停在绿色）。
  - **恢复信号必须发给两个面板**：`sigMotionTerminate`（完成帧/超时/停止/应答异常四条路）、`sigLightOffFinish`（0x0E 到时帧）在 `SetConnectSlot(true)` 里都接了两个实例；只接运行页的话，在配置窗口发的那一条跑完后，那个面板的"发送"会一直是灰的。
  - **两个面板的运行态要互相同步**：`SyncRunButtonStates(const ControlPanel*)` 只抄"发送/停止 + 料仓一对 + 光源四对"的 enabled（**不抄**序列计数、看门狗、运动类型键），并且与目标面板的 `m_bRunEnabled` 取与（没连接时抄进来的"可点"必须压掉）。调用点：打开配置窗口时运行页 → 配置页，关闭时配置页 → 运行页。
  - **凡是问"有没有动作在跑"的地方都要看两个面板**：`ApplyConfiguration()`（否则在窗口里试跑时应用会中途换参数）、`closeEvent()` 的退出确认（否则会漏掉"窗口里那条还在跑"）。`IsBinRunning()` 单独提供，避免 `IsMotionRunning()` 把料仓也算进运动灯。
- **运动进行中的"运动类型按钮全锁"（2026-11-23）**：点"发送运动"或 G1/G2 之后，`pbUp/pbDown/pbLeft/pbRight/pbGather/pbHCentered/pbVCentered/pbDisperse/pbFlip` **九个运动类型按钮一起 `setEnabled(false)`**，只有三条路能解锁：① 下位机完成帧（`sigMotionTerminate`）；② 运动反馈超时（引擎在 `OnEngineTick()` 清队后**仍发** `sigMotionTerminate`）；③ 用户点"停止运动"（引擎清运动队列时发 `sigMotionTerminate`）。实现集中在三个私有函数：`SetMotionTypeButtonsEnabled()`（只开关 9 个按钮）、`LockMotionUi()`（发送键禁用 + 停止键使能 + G1/G2 与 9 个按钮置灰 + `m_bMotionUiLocked = true`）、`RestoreIdleButtons()`（唯一解锁点，同时恢复料仓/光源按钮）。调用点：`on_pbSendMotion_clicked()` / `StartGroupMotionSequence()` 里 `LockMotionUi()`；terminate lambda、`m_pMotionSeqWatchdog` 超时、`ResetMotionUiState()` 里 `RestoreIdleButtons()`。
  - **不改选中项**：`QAbstractButton::setEnabled(false)` 不会清 `checked`，所以 `m_qstrCurrentMotionButton` 与界面选中态在解锁后天然一致；`RestoreIdleButtons()` 里还加了一条兜底——若 `m_pMotionGroup->checkedButton() == nullptr`，按 `m_qstrCurrentMotionButton` 补一次 `setChecked(true)`（否则"发送运动"会因没有当前按钮而静默无反应）。
  - **为什么锁**：参数编辑器（`dspbVoltage/dspbFrequency/dspbTime/cbMotionKeep`）只有一套、跟着"当前选中按钮"走，运动进行中允许改选会造成"界面显示 A、实际在跑 B"；同时挡住连点重复下发（`on_pbSendMotion_clicked()` 入口另有 `m_bMotionUiLocked` 早退兜底）。
  - **锁的粒度是"按钮可点性"，不是"真实运动状态"**：`IsMotionRunning()` 现在把 `m_bMotionUiLocked` 也算进去。
  - **已知边界**：引擎的 `sigMotionTerminate` 是振动盘运动、料仓运动、料仓停止三条路径**共用**的，因此"料仓运动完成"也会走 `RestoreIdleButtons()`，理论上会在振动盘运动还在跑时提前解锁运动类型按钮（属既有的粗粒度设计，本次未拆信号）。要彻底分开需在 `ConnectiveHandle` 增一个"仅振动盘完成"的信号，动静比这次大。

- **固件参数页的"读/存互斥"（2026-11-23）**：`pbGetKeyParams` / `pbSaveKeyParams` 的使能条件是 `m_bKeyParamsAvailable && !m_bKeyParamsPending`——两个按钮**要么都可点、要么都变灰**，不允许"一边在等应答、另一边还能再发"。`m_bKeyParamsAvailable` 由 `ControlWidget` 在连接成功（`OnConnectiveState(true)`）时置 true、`CloseConnection()` 里经 `ResetKeyParamsUiState()` 清掉；点击后立刻 `m_bKeyParamsPending = true` 并刷新 `lbKeyParamsStatus` 文案（"正在从下位机读取…"/"正在保存到 Flash…"），等 0x16/0x18 回来或超时才置回 false。
  - 引擎侧的 `SendGetKeyParamsCommand()/SendSaveKeyParamsCommand()` 里还有一道"队列非空就 return"的兜底，**重复点击不会堆叠指令**（界面变灰只是第一道闸）。
  - **超时必须回报**：`OnEngineTick()` 两个分支超时后分别发 `sigGetKeyParamsResult(0xFF, 空)` / `sigSaveKeyParamsResult(-1)`。漏了的话 `m_bKeyParamsPending` 永远为 true、按钮永久置灰——与本节开头那条"唯一恢复点"是同一类教训。
  - **只读面板上这两个按钮也必须亮**：`m_pModeWidget` 打开初期是 `SetReadOnly(true)`（= `SetRunEnabled(false)`），但固件参数页读写的是下位机 Flash、不动本地配置，所以 `on_pbGetKeyParams_clicked()/on_pbSaveKeyParams_clicked()` **故意没有 `m_bRunEnabled` 早退**，只受 `m_bKeyParamsAvailable`（是否已连接）约束，`ControlWidget` 也把两个面板的信号都接了。**别顺手给它们补上早退**，补了就变成"控制页能用、模式页点了没反应"。
  - 12 个编辑器统一 `setDecimals(4)`，理由见第 9 节。

- 料仓：开始→禁开始/使停止；停止由引擎清队列后发 terminate 恢复。
- 光源：开→禁开/使关；关→使开/禁关；**保持时间到时下位机自发 `0x0E` 带索引完成帧，引擎经 `sigLightOffFinish` 复位对应路按钮**（A/B/C/D 独立；0=全关四路一起恢复）。关闭指令的应答匹配兼容两种来源：期望带索引时仅同索引完成帧可收，期望全关时任何 0x0E（含到时自发帧）都算完成；到时帧同时透传给界面。按钮状态含义为"该路是否处于开启指令保持期"，仍不是真实灯态探测。

- **「保持」勾选框（2026-11-22，7 个：`cbMotionKeep` / `cbBinKeep` / `cbLightAKeep` / `cbLightBKeep` / `cbLightCKeep` / `cbLightDKeep`）**：
  - 位置：紧跟在各自的时间 spinbox 后面（`.ui` 里把原来单独的时间行改成了 `QHBoxLayout hblMotionTimeRow / hblBinTimeRow / hblLightXTimeRow`），文字「保持」，**默认不勾选**（=下发 0，按时间动作）。
  - 归属：它们是**参数编辑器**，和电压/频率/时间同一类——运行页（`bFlatRun`）里随编辑器一起隐藏但数值仍参与取值（隐藏循环里加了 `QCheckBox *` 分支，漏加会出现"运行页上多出一个孤零零的勾选框"）。
  - **运动区是"几个按钮共用一套设置"**：`cbMotionKeep` 只有一份，切换选中的运动按钮时由 `OnMotionGroupButtonClicked()` 的刷新循环 `setChecked(该按钮的 keep)`；用户勾/取消由槽 `on_cbMotionKeep_toggled()` 写回当前选中按钮的 `qlstMotionParams.first()["keep"]`。该 connect 必须**手动加在构造函数**里（`setupUi(parent)` 导致自动连接失效，见第 9 节）。
  - 料仓/光源的勾选框直接读控件，不进按钮存储结构（料仓/光源各只有一套参数）。

### 配置持久化（ini）

- 振动盘 9 个按钮：`[MotionXxx]` 组（frequency/timeuse/voltage/angle_offset/speed/**keep**）。
- 料仓：`[BinMotion]` 组（voltage/frequency/timeuse/**keep**）；光源：`[LightA]`/`[LightB]`/`[LightC]`/`[LightD]` 组（brightness/timeuse/**keep**）。C/D 的旧配置缺键时明确回落为 0，避免切换配置后串用上一份的 C/D 参数；默认亮度 0 不自动点灯，保持时间 0 沿用常亮语义。
- `keep` 键（2026-11-22 新增）存 **0/1 整数**，缺键一律按 0（=按时间动作）——老配置文件无需迁移。
- 三个入口必须同步维护：`SaveSettings()`（写全部组）、`GetSettingParams()`（读；A/B 键缺失时回落到控件当前值，C/D 缺键时回落到 0）、`CopyButtonParams()`（模式↔控制互拷，直接拷 spinbox 值）。**新增任何可保存的 UI 参数，三处都要加**。
- `CopyButtonParams()` 的两条铁律（2026-10-29 修过 bug 的教训）：
  1. **禁止 `m_lstMotionButtons = other.m_lstMotionButtons` 整表赋值**——会把对方面板的 `pButton` 指针拷过来，本面板运动按钮从此选不中；必须按 `qstrName` 匹配逐按钮拷 `qlstMotionParams`；
  2. **UI 全量刷新所有按钮参数时必须用 `QSignalBlocker` 屏蔽 valueChanged**——运动参数控件组只有一套，刷新循环里 `setValue` 会触发槽，槽把遍历值写进选中按钮的存储参数（数据污染）；屏蔽后最终界面停留为最后一个按钮的值，存储数据不受影响。
- `NewSettings()` 以 `DefaultConfigRaw.ini` 为模板复制（该文件不在仓库时 QSettings 落空），`SaveSettings(QString)` 先复制当前文件再全量重写。仓库里的 `DefaultConfig.ini` 已含 `[BinMotion]/[LightA]/[LightB]` 默认段。

1. `generalprotocol.h`：加 `u8SW_XXX_CMD` / `u8FW_XXX_RESPOND` 常量；
2. `ProtocolHandle.h`：加虚函数（给默认空实现，避免破坏可编译性）；`GeneralProtocol` override 实现组帧（发送帧 + 期望应答帧成对生成，走 `AddCheckSum`）；

4. `controlpanel`：加 UI 槽（组帧 + emit + 按钮互锁），信号加到头文件；**并在构造函数"连接按钮事件"段手动 `connect(ui->pbXxx, SIGNAL(clicked()), this, SLOT(on_pbXxx_clicked()))`——本类因 `setupUi(parent)` 导致自动连接失效，漏这一行按钮就是死的（见第 9 节）**；
5. `controlwidget.cpp` 的 `SetConnectSlot(true)`：连接信号槽；`OnConnectiveUnnormal()`：加异常分支（弹窗文案 + 统一 terminate）；
6. `doc/通信协议.docx` 与本文件同步更新。

**给已有指令加字段（比新增指令更危险，长度变了）**：①`generalprotocol.cpp` 组帧末尾追加字节 → ②期望应答帧**不变**（应答里没有这些字段，不要顺手改）→ ③上位机若从帧里反推（如超时用的是 `帧[9][10]`），确认偏移没被顶掉 → ④下位机解析**一律按长度域定位、不要写死下标**（`SerialHandle.c` 里 2026-11-22 的 `u8InfiniteTime` 就是范例）→ ⑤`ConnectiveHandle.cpp` 里"从尾部找数据字节"的助手（`IsInfiniteTimeFrame()` 用 `size()-5`）也要跟着核对 → ⑥表里的长度、§9 的长度备注、docx 三处一起改。**漏一步的表现通常是"静默匹配失败 → 一律超时"，不会有编译错误。**

## 9. 已知怪癖与坑（改动前必读）

- **⚠️ 两个面板同控一台机器：所有"运行状态"都要成对处理（2026-11-25 二十次）**：`ControlPanel` 现在有**两个活实例**（运行页 `m_pControlWidget` + 配置窗口 `m_pModeWidget`），都能下发。这次踩到的四个坑都是"只处理了一半"：
  - **禁用判据写在两个地方就会打架**：原来每个下发槽里都写着 `if (m_bReadOnly) return;`，改成"配置面板也能发"时若只放开按钮、不改判据，表现就是**按钮能点但发不出去**（或者反过来，发了却卡在锁定态）。现在统一看 `m_bRunEnabled`，`SetReadOnly()` 只是它的兼容入口 —— 新增下发路径时**只能用 `m_bRunEnabled`，不要再引第三种状态**。
  - **同步按钮态必须和"能否下发"取与**：`SyncRunButtonStates()` 只照抄 `isEnabled()` 时，把一个**未连接**的配置面板抄成了"可点"（因为运行页此时是可点的），点了发不出去、按钮还锁死。写法：`dst->setEnabled(m_bRunEnabled && src->isEnabled())`。
  - **断连时的复位顺序**：`ResetMotionUiState()`（内部 `RestoreIdleButtons()` → 刷状态灯）必须在 `SetRunEnabled(false)` **之前**调。反过来的话，`RestoreIdleButtons()`/`NotifyRunState()` 里"未连接就早退"的判据会把这次复位挡掉，状态灯停在绿色而按钮已经全灰 —— 这是最容易被忽略的一种不一致。
  - **`NotifyRunState()` 不要按"能否下发"早退**：它算的是"按钮现在是什么状态"，禁用之后算出来天然就是"两盏灯都灰"，正是需要发出去的那一帧。早退等于丢了断连时的熄灯通知。
- **⚠️ `QPushButton` 的水平 sizePolicy 是 `Minimum`，`addWidget` 进布局就会被拉长（2026-11-25 十八次）**：`sizeHint` 只是**下限**，布局一旦有余量它照样长。配置窗口顶部四个模式键原来就是这样被窗口宽度等分成四条长条。要"只装得下文字、绝不拉伸"，用 `setFixedSize(宽, 高)`（把 min/max 都锁死），并在行尾补 `addStretch(1)` 把富余宽度甩到右边；只 `setFixedWidth` 也行，但高度不锁时 `QPushButton` 的垂直策略也是 `Fixed`，取 `sizeHint`（25px）—— 想稳妥就连高度一起锁。
- **⚠️ `QDialog` 的默认尺寸别写死，用 `adjustSize()` + `setMinimumSize(sizeHint())`（2026-11-25 十八次）**：写死 `resize(1050, 720)` 在不同窗口/字号下不是太大（一片空白）就是太小（内容被压）。组装完所有控件后 `adjustSize()` 会按 layout 的 `sizeHint` 取"刚好装下"的尺寸，再把该 `sizeHint` 设为最小值 —— 打开即最小、能放大、缩不小。**注意顺序**：必须在 `pLayout->addWidget(...)` 全部做完之后调，否则量到的是半成品。
- **⚠️ `TitleBar::kBarHeight` 和 `kBtnHeight` 必须成对改（2026-11-25 二十一次）**：标题栏高度在 `titlebar.h`（`kBarHeight`），三个窗口按钮高度在 `titlebar.cpp` 的匿名命名空间（`kBtnHeight`），按钮上下留白是 `(kBarHeight - kBtnHeight) / 2` 算出来的。只改前者不改后者，按钮会顶满整条、或者算出 1px 留白看着像三个色块；反过来只改后者，按钮会在条里上下不对称地漂。**改完用 `titlebar_only.png` + `titlebar_buttons3x.png` 两张图核**：前者看整条比例与 logo/文字是否居中，后者看图标有没有被 32 高的小按钮裁掉。
- **光源状态灯的初始状态要"装配完再刷"（2026-11-25 十二次实测）**：在四组还没 `addLayout` 完、组件树半成品的时候给灯 `setPixmap`/`SetLightLamp`，出现过 **`LightGroupB` 宽度算成 0、整组在界面上消失**（`light_geo.txt` 里能看到 `kid geo=113,100 0x78`）。现在把初始状态统一放到四组摆完之后调一次 `SetAllLightLampsOff()`，四组几何稳定为 `176x78`。以后再动这块，**先看 `light_geo.txt` 四个 kid 是不是都有 176 宽**。
  - **这个现象在"重新链接后的第一次运行"仍会偶发**（2026-11-25 十七次又中一次：A 组 `0x78`、截图缺 A 组、进程还 SIGSEGV 退出码 139），**第二次跑就正常**。所以：① 截图少一组、几何里某 kid 宽度为 0 时，先**重跑一次**再判定是不是真 bug；② 别据此改代码。
    - **gdb 栈**（十八次抓到的）：崩在 `QStyleSheetStyle::polish(QWidget*)` → `setPalette` 里，外层是 `QWidget::ensurePolished()` ← `QLayout::totalSizeHint()` ← `QGridLayout::minimumSize()/sizeHint()` 层层嵌套 —— 也就是"计算尺寸时触发样式表 polish、polish 又要算尺寸"的深递归。冷启动（新链接的 exe 首次执行、杀软在扫文件）时耗时变长、时序不同才踩到，热起来后 8/8 次都正常。**属 Qt 样式表内部的时序问题，不是业务代码 bug**；见到"刚编译完第一次启动就闪退"直接再启动一次即可。
- **⚠️ `DefaultConfig.ini` 缺失时点任何运动键都会崩（2026-11-25 十三次踩到）**：`ControlPanel::GetSettingParams()` 在 `QFile::exists()` 为假时**直接 return**，`m_lstMotionButtons` 里每一项的 `qlstMotionParams` 于是都是空列表；而 `OnMotionGroupButtonClicked()` 一进来就 `Button.qlstMotionParams.first()` —— 空 `QList::first()` 是未定义行为，实测 **SIGSEGV 直接闪退**（gdb 栈：`QButtonGroup::buttonClicked` → 我们的槽）。
  - 现在槽里加了 `if (Button.qlstMotionParams.isEmpty()) continue;`，宁可这一次不响应也不闪退。
  - **跑截图/自测时注意**：`build-check/theme` 这类构建目录必须放一份 `DefaultConfig.ini`（从工程根目录拷），否则界面能开、一点运动键就崩，很容易误判成"新加的灯把程序搞崩了"。
- **⚠️ 一格装一个 item 的 `QGridLayout`，再加一行会被"平摊"（2026-11-25 十三次）**：`groupBox_3` 的 `gridLayout_18` 原本只有「电压(V)」一个 item，直接 `addWidget` 加第二行，网格把卡片高度按行平分 → 两行分居卡片上下、中间空一大块，看着像两件不相干的东西。要"两行紧挨、整体居中"，得显式加两个纵向 Expanding 弹簧（上/下各一，`setRowStretch` 1）并把中间两行 stretch 设 0。
  - **换格子不等于删东西**：`gridLayout_18->itemAtPosition(0,0)->layout()` 拿到的就是「电压(V)」那行的子布局本身，`removeItem()` 之后 `addLayout(layout, 1, 0)` 放回去即可 —— **布局对象和它里面的控件都不删**，`label_4`/`leVoltage` 照旧工作。
- **⚠️ 卡片"长不宽"往往是中间那道 Expanding 空占位在吃宽度（2026-11-25 十四次）**：`gridLayout` 是 `[连接方式 col0] [horizontalSpacer_5 col1] [状态卡 col2]`，col1 那道 Expanding 空占位实测吃掉 291px，col2 的卡片只按自己的 sizeHint（278）取宽 —— 于是往卡里塞一行内容时，内容明明只要 520，卡片却怎么也长不到，表现为文字挤成一团/被裁。解法：`horizontalSpacer_5->changeSize(0,0,QSizePolicy::Fixed,QSizePolicy::Minimum)` + `setColumnStretch(2,1)`（改完记得 `gridLayout->invalidate()`，构造期在 show 之前也要，否则第一次布局用的还是旧几何）。
- **`RightToLeft` 的 QLabel 在 `QGridLayout` 里会独占整列**：`label_4`（「电压(V)」，`layoutDirection=RightToLeft` 让文字贴右、紧挨输入框）原来被网格分到 191px 宽 —— 文字只有 43（16px 时 55）。要省宽度就 `setSizePolicy(QSizePolicy::Fixed, QSizePolicy::Preferred)`，它会缩回文字宽，多出来的全归后面的控件。
- **⚠️ 给一行字放大号之前，先算"这行要吃掉邻居多少"（2026-11-25 十五次实测）**：状态行按"12px × 1.5 = 18px 加粗"排，实测一行要 **757px**；而 1200 宽的窗口里，状态卡最多只能从「连接方式」卡手里抢到 561 —— 结果连接方式卡被压到 **361px，IP 输入框只剩 "2.199"**，界面直接坏掉。两条教训：
  - **宽度的账要按"两张卡之和"算**，不是只看状态卡自己的 sizeHint。默认窗口宽度（`.ui` 的 geometry）是硬约束，改不动字号就得改窗口宽度：这次把 1200 提到 1400，`589 + 757 = 1346 < 1364` 才容下。
  - **字号听用户的，但具体像素要自己验证**：最后取 16px 加粗（1.33 倍），一行 696，卡片 757，连接方式卡 589 一点没被压 —— 视觉上已经比 12px 明显醒目，比硬凑 18px 把界面挤坏划算。
- **QSS 的 `font-size` 会盖掉 `QFont::setPixelSize`**：`app.qss` 里 `QWidget { font-size: 12px }` 是全局的，想在代码里 `setFont()` 放大状态行是无效的（会被样式表覆盖）。要改这一行的字号，只能写进 `app.qss`，并且**按 objectName 列名单**（`label_4`、`StatusLampName0..2`、`StatusSoftVersion(Name)`、`StatusFirmVersion(Name)`）—— 用 `QWidget#StatusLampRow QLabel` 这种后代选择器**选不中 `label_4`/`leVoltage`**：它们是 `addLayout` 进这一行的，父子关系还挂在 `groupBox_3` 上。
- **`build-check/titlebar_shot.sh` 刚链接完就立刻运行，第一跑可能 SIGSEGV**：只发生在刚重新链接的那一次，紧接着再跑就正常（文件刚写完被杀软/缓存抢着读的典型症状），不是程序 bug。写脚本时别把"第一跑崩了"当成回归。

- **⚠️ Qt Designer 会"吃掉"空容器 QWidget（2026-11-25 踩到）**：在 Designer 里保存 `.ui` 时，凡是**没有属性、只装一个布局**的 QWidget，Designer 会自动把它删除，并把里面的布局提上一层。uic 随后不再生成这个成员，代码里 `ui->xxx` 立刻变成 `no member named 'xxx' in 'Ui::ControlWidget'`。
  - **触发场景**：为了让布局多一层边距/容器而在 Designer 里插了个 QWidget，或在代码里给某个 QWidget 加了 objectName 并依赖它——只要它在 .ui 里"没有任何 property"，下次在 Designer 里一保存就没了。
  - **现在的受害者**：`tabPanel`（已删）、`tabControl`、`tabMode`。控制内容改用 `ControlTabWidget` 作为禁用锚点，模式面板用 `ModeTabWidget` + `gridLayout_13` 收放。
  - **想保住容器就给它一个属性**（例如 `sizePolicy`），纯空壳保不住；**更稳的做法是不要依赖这类容器**，改用里面有实际控件/属性的那个 widget 或布局。
  - **判断方法**：报 `no member` 时先看构建目录的 `ui_xxx.h` 里还有没有这个名字——没有就说明 .ui 被 Designer 改过，而不是代码写错。
- **⚠️ 无边框窗口（2026-11-24 自绘标题栏引入）的四条硬约束**：
  1. **`setWindowFlags()` 会让窗口隐藏并重建原生窗口**——只能在构造期（`show()` 之前）调，放到别处会出现"窗口闪一下/不见了"。现在写在 `ControlWidget` 构造函数 `setupUi` 之后。
  2. **`showMaximized()` 不能再用**：无边框窗口按 `screenGeometry` 铺满，会把任务栏盖掉，现场点不到开始菜单。统一走 `TitleBar::SetMaximized(true)`（用 `availableGeometry`），`main.cpp` 的小屏防御也改成 `w.MaximizeToScreen()`。
  3. **手动 `setGeometry` 的"最大化" Qt 不认**：`QWidget::isMaximized()` 返回 false，`QSizeGrip` 不会自动隐藏。必须由 `TitleBar` emit `MaximizedChanged(bool)`，`ControlWidget` 收到后收放握把。
  4. **最大化尺寸会被 `minimumSize` 钳制**：窗口 min 是 1000×740，本机可用区只有 1094×735，最大化后高度会溢出屏幕 5px。现场 1080p 及以上不会触发；若日后要支持更小屏，得先降 `minimumSize` 或把内容改成可压缩布局。
- **标题栏截图验证要按像素放大看**：拉丝只有 1px 宽，`SmoothTransformation` 缩放的样张会把纹理糊成"没有"。`build-check/build_titlebar_shot.sh` 生成 `titlebar_pixel4x.png`（4 倍最近邻）就是干这个的。另外窗口比屏幕大时 `QWidget::grab()` 仍能抓全，但**屏幕截图会被裁**，别拿屏幕截图判断布局。

- **⚠️ QSS 的 `::up-arrow` 必须显式给形状（2026-11-24 踩过）**：只要给 `QSpinBox::up-button/down-button` 设了任何属性，Qt 就完全用样式表绘制这两个子控件；此时若 `::up-arrow/::down-arrow` 既不写 `image` 也不写边框形状，**箭头会整个消失**，表现为数值框右侧一条空白窄条（还能点，只是看不见）。现用"零尺寸盒子 + 三条边框拼三角形"的写法（`style/app.qss`），不依赖图片，也不受高 DPI 下位图模糊影响。**换肤类改动必须离屏截图逐页核对，这类问题编译期零报错。**
- **样式表只许一个出口**：除随数据变色的 `SetKeyParamsStatus()` 外，不得在 cpp 里写 `setStyleSheet`。内联样式优先级高于应用级样式表，散着写必然出现"改了全局没反应 / 局部和全局打架"。新增按钮要配样式，就在 `app.qss` 里按 objectName 加规则；`.ui` 里的 objectName **不要改名**，改了样式静默失效。
- **给某个控件类设 QSS 属性 = 接管该类全部绘制**：`:hover / :pressed / :checked / :disabled` 四种状态必须写全，漏一个就是"按下去没反馈"。**`:disabled` 是现场硬需求**（"能不能按"要一眼看出），配色必须比原生更明显，别为了"淡雅"把它调浅。
- **⚠️ QIcon 少给一种 mode/state 就会「回退错色」（2026-11-24 踩过）**：`QPushButton` 画图标时按 `mode = 悬停?Active:Normal`、`state = 选中?On:Off`、禁用则 `Disabled` 取图，共 **4 mode × 2 state**。只给 `Normal/Off` 时，选中态（实心蓝底）会回退成绿色图标，绿压蓝糊成一团；禁用态则会回退成彩色。`ControlPanel::MakeMotionIcon()` 把 8 种组合全 `addPixmap` 了，加新图标别偷懒。
- **⚠️ `QPushButton` 的垂直 sizePolicy 是 `Fixed`，不显式给高度就只占 `sizeHint`（2026-11-24 踩过）**：同一行里的方块键都 `setFixedSize(64,64)`，`发送运动/停止` 只设了 `setFixedWidth(104)`，结果它们高度只有 **25px**，在 64 高的行里垂直居中成一条小扁条，看着像没做完的半成品。同排控件要等高，必须自己 `setFixedHeight`/`setFixedSize`，布局不会帮你对齐。
- **⚠️ 别在运行时直接 `QIcon("*.svg")`**：那是走 `qsvgicon` 插件，现场部署要多带 `iconengines/` 目录，少拷一个文件按钮就变空白（而 exe 本身照常启动，极难查）。本项目统一「SVG 只当素材源 → 离线光栅化成 PNG → 编进 qrc」，PNG 解码是 QtGui 内置能力，零插件依赖。
- **还有一处没被 QSS 覆盖**：`dialAngleRegulation`（角度调节旋钮）是 `QDial`，它没有可用的 QSS 子控件，native 立体斜边会一直在，是当前界面上最"旧"的一个构件。要彻底统一得换成自绘旋钮或改用滑条（属结构性改动，本轮未做）。

- **TIM3 被三个模块共用**，改动前先明确通道归属：CH1/CH2 = 料仓（PA6/PA7，双极性振动，走 CC 中断查表）；CH3/CH4 = 光源A/B（PB0/PB1，纯电平）。
  - 由此产生三条铁律：①**任何模块都不许调用 `HAL_TIM_PWM_Stop()/Stop_IT()`**（见 `stm32f1xx_hal_tim.c:1690`，结尾 `__HAL_TIM_DISABLE(htim)` 关掉 CEN，把另两个模块的输出冻死）；②起停通道优先手动操作 `CCxE`/`CCxIE`/`CCR`，计数器只用 `__HAL_TIM_ENABLE`；③关输出只用 `CCR=0`，不要动 `CCxE`。
  - **料仓的起振改用 HAL 的 `HAL_TIM_PWM_Start_IT()`（2026-10-30，开关 `BIN_USE_HAL_START_IT`）**。它可用，但有两个硬约束：`Start_IT` 在 `stm32f1xx_hal_tim.c:1552` 判断 `ChannelState != READY` 就直接 `return HAL_ERROR`（不写寄存器、不打日志），所以调用前必须 `TIM_CHANNEL_STATE_SET(..., READY)`；而复位状态**不能**用 `Stop_IT`，只能在 `BinPwmStop()` / `BinSwitchChannel()` 里手工写 READY。**两者配对才能重复启停，缺一必出现"第一次能振、之后怎么点都不动"。**
- **`MotorControl()` 末尾原来每轮写 `__HAL_TIM_SET_COMPARE(&htim3, TIM_CHANNEL_3, u16PwmLED)`**（`u16PwmLED` 恒为 0 的调试残留），而 CH3 现在是光源A 的亮度通道——已在 2026-10-29 删除。若日后又出现"灯亮了立刻灭"，先查有没有别处每轮写 CCR3。
- **`sMotor[4]` 是料仓的硬件映射但 `pActivePolarity` 从未初始化（NULL）**：`HAL_TIM_PWM_PulseFinishedCallback` 的遍历已从 `i<5` 改为 `i<4`。若改回 5，会解引用空指针，并且和 BinControl 抢写同一个 CCR。
- **停止指令必须复位状态机**：`BinControlStop()` 里 `g_eBinStep = BIN_STEP_GET_INFO`。否则 `pControlFunc` 已置 `BinMoveNone`（立即返回 true），下一轮主循环会误发一帧"运动完成"0x08。
- **⚠️ 料仓"点了没振动"的头号原因：运动时长为 0**（2026-10-30 复算确认）。`PrepareBinMotion()` 里起振与否的**唯一判据**是 `if (u32TimeUseMs > 0) BinPwmStart();`，而 `u32TimeUseMs = fTimeUse * 1000`。`DefaultConfig.ini` 的 `[BinMotion] timeuse=0`、UI 里 `dspbBinTime` 也没设默认值（QDoubleSpinBox 默认 0.0）→ **默认下发的一定是 0** → 不起振、不使能、不写 CCR，下一次 `BinRun()` 直接判完成并回 0x08；上位机因立刻收到应答**不会报超时**，表现为"一切正常但就是不振动"。

  - 参考占空比峰值：`DutyZoom = V/24*32768`，V=10 → 峰值占空比 1875/4499 ≈ **41.7%**；V=24 → 满占空比。
- **MOS 使能 `ENABLE_BIN`/`BIN_ENABLE`（PA8）是低电平有效：`(0)`=使能导通，`(1)`=失能关断**（用户 2026-10-30 确认）。佐证：`gpio.c:59` 上电把该脚初始化为 `GPIO_PIN_SET`（默认关断），用户旧的 `MoveBin()` 测试代码里第一步也是 `ENABLE_BIN(0)`。**因此 `BinPwmStart()` 里的 `BIN_ENABLE(1)` 实际是失能 MOS**——这一处极性存疑，是"料仓不振动"的重点嫌疑仅次于运动时长=0，**暂按用户要求未改，待确认**。`BinControlInit()`/`BinControlStop()` 目前不操作该脚（2026-10-30 已撤销先前误加的调用）。

- **运行页三区（`ControlPanel(parent, bFlatRun=true)`）是纯代码布局，改标题/边距前先读 `controlpanel.cpp` 构造函数开头**：标题条是 `QLabel` 不是 QGroupBox 标题（QGroupBox 标题已清空，避免同一个词显示两遍）；标题条必须"定高 + 纵向 Fixed"，否则 `QVBoxLayout` 会把整列富余高度灌给它，表现为"标题下面一大块空白"（2026-11-21 踩过，见日志）。同理，任何 `addWidget` 进竖直布局的装饰性 Label 都要显式给 SizePolicy。

- **⚠️ 发送缓冲的两个宏必须装得下最长的帧（2026-11-23 因 0x16 扩容）**：`SerialHandle.h::UART_SEND_DATA_LEN` 32 → **64**，`SerialHandle.c::RESPOND_FRAME_MAX_SIZE` 16 → **64**。0x16 应答整帧 = `55 AA` + cmd 1 + len 1 + 数据 49 + 校验 2 + `AA 55` = **57 字节**，原来的 32/16 会把后半截**静默截断**（往定长缓冲里写超长内容不报错、也不进 HardFault），表现是"下位机看起来正常回帧了、上位机却等到 2s 超时"，极难定位。以后再加长帧指令，先算 `数据域长度 + 9`，再确认这两个宏与网络侧 `NETWORK_SEND_DATA_LEN`/`NETWORK_FRAME_DATA_LEN`（都是 64）都够。
- **⚠️ 长帧被 DMA/IDLE 切成两段会整帧丢失（2026-11-23 修复，症状是"保存固件参数超时"）**：接收状态机原本是"找到帧头 55 AA → **逐字节扫描**找帧尾 AA 55"，扫描每 tick 只前进 1 字节，扫到 `writeIndex`（数据边界）还没找到帧尾就放弃，而此时 `readIndex` 已经前进到帧中间——后半段数据到达后从帧中间再也找不到 `55 AA`，整帧被逐字节丢弃，下位机不回帧，上位机 3s 后报超时。
  - **为什么只有 0x17 中招**：`0x15`（获取）上行只有 9 字节，一包发完，永远不会被切开；`0x17`（保存）上行 **57 字节**，USB 转 485 适配器在包边界处会产生 >1 字符的空闲，DMA 的 IDLE 中断因此触发两次，正好把帧切成两段。
  - **修法**：新增 `UartRecvFrameReady()`，在进扫描前先用长度域算整帧长度（`数据域长度 + 8`），`u16Avail < u16FrameLen` 就**退回等数据、`readIndex` 保持在帧头不动**；收齐后直接进 `PARSE_DATA`，并按整帧长度推进 `readIndex`，不再扫描帧尾。
  - **顺带堵掉的两个隐患**：①数据域里恰好出现 `AA 55` 时扫描会提前截断（0x17 的 48 字节是任意 float 数据，出现该组合是现实的），按长度推进后不再受影响；②`u16WriteIndex = 缓冲区大小 - DMA计数器` 在收满整个缓冲（计数器为 0）时会等于 256，与 `readIndex`(0~255) **永不相等 → 状态机死锁**，已加取模。
  - **回归测试**：`build-check/rbt6_recvframe_test/`（`#include` 真实 `SerialHandle.c`，桩掉 DMA/HAL）**26 项全 PASS**，覆盖 57 字节整帧、9 字节短帧、切成 2 段/3 段、数据域含 `AA 55` 且紧跟下一帧、垃圾前缀、短帧切 5+4。**改动前后对比：修复前"切成两段"两项 FAIL，修复后全 PASS。**
- **固件参数页的 4 位小数是硬要求，不是审美（2026-11-23）**：下位机默认值里有 `0.4375`（= 7/16）。`QDoubleSpinBox` 默认 2 位小数 → 显示 `0.44`；3 位 → `0.438`。用户点一次"保存配置"就把**舍入后的值**写进 Flash——界面悄悄改了参数，下一轮读回来也是这个错值，肉眼几乎发现不了。取 4 位后 `1.375 / 0.4375 / 0.25 / 0.5` 全部精确（这些数在二进制里本就是精确的 1/16 整数倍），读写都不漂。**改 `setDecimals()` 之前先看 `KeyParameters.c` 的默认值表。**
- **固件参数的 Flash 页不许和别人撞**：`KeyParameters.c` 用 `0x0800F800`（第 63 页），`SaveParams.c` 用 `0x0800FC00`（第 64 页），中容量 F103 是 1KB/页，各占一页互不干扰。新的参数块**必须自己占整页**（擦除按页做，挤在别人页里会顺手把它擦掉），并从高地址往前分配。`KEY_PARAMS_FLASH_ADDR` 用 `#ifndef` 包着是为了宿主机单元测试能覆盖成内存数组，**别改成裸 `#define`**。
- **`SaveParams.c` 的校验套路要照抄**：擦页 → 半字编程 → **回读 `memcmp` 比对**。只看 `HAL_FLASH_Program()` 返回值不够（返回 `HAL_OK` 而实际没写进去是遇到过的）；`SaveKeyParams()` 里回读不一致就返回 false 且**不更新 RAM 里的当前值**——否则界面显示新值、Flash 里还是旧的，重启后又变回去，这类 bug 最难查。
- **全局参数必须在上电时主动加载一次，不能"等指令来触发"（2026-11-23）**：`g_sKeyParams` 是 BSS 段变量，上电初值**全 0**，而 0 是"看着合理、实际有害"的相位（电机抖动/不出力）。原来只有 `GetKeyParamsHandler()` 收到 0x15 才填它，意味着**上位机连上之前、或者从上位机界面上直接点"发送运动"而没先点"获取配置"**时，电机用的是全 0 相位。修法是在 `FlexControlInit()` 里 `SaveParamsInit()` 之后调一次 `GetKeyParams()`。更一般地说：**凡是"上电后随时可能被消费、而 Flash 里有持久值"的参数，都要在 `FlexControlInit()` 里主动加载**，别指望协议指令来驱动（`SaveParams` 的 IP 就是这么做的——`SaveParamsInit()` 先于 `NetworkInit()`）。

- **2026-11-23 修复「保存固件参数一直超时」（下位机串口长帧接收，`SerialHandle.c`）**：
  - **现象**：上板后点「保存配置」，上位机 3s 报**保存超时**；「获取配置」正常。（用户第一反应怀疑 `u8SAVE_KEY_PARAMS_SUCCESS` 取反，**排除**：该常量只决定"收到 0x18 之后"按成功还是失败处理，若它有问题看到的是"保存失败"而不是"超时"。超时的唯一含义是 3s 内没收到可匹配的 0x18。）
  - **排查过程**：上位机侧逐段核对无误——`SendSaveKeyParamsCommand()` 入队 → `OnEngineTick()` 只在 `WriteData()` 返回 true 后才置 `bSent` 并开始计时 → 3s 无 `bRespond` 才 emit `-1`，所以**帧确实发出去了**，缺的是下位机的 0x18。下位机侧 `ParseUartData()` 的偏移（`DataIndex+3` 跳过标志字节）/长度（==49）/16 位校验、`SaveKeyParams()` 的擦写与回读比对、`SaveRespondFrame(0x18, ...)` 的组帧也都正确。静态读代码查不出问题，于是**给接收路径补了宿主机测试**（`#include` 真实的 `SerialHandle.c`，桩掉 DMA/HAL）→ 立刻复现：57 字节帧**一次到齐能解析，切成两段就整帧丢失**。
  - **根因**：`UartRecvBufferHandler()` 用"逐字节扫描找帧尾 AA 55"确定帧结束。扫描每 tick 只前进 1 字节，数据还没收全时扫到 `writeIndex` 就放弃，**而 `readIndex` 已经移到帧中间**；后半段到达后从帧中间找不到 `55 AA`，整帧被丢弃。0x15 只有 9 字节一包发完，0x17 有 57 字节，被 USB/IDLE 切成两段 → 只有保存超时。详见 §9。
  - **修复（三处，都在 `UartRecvBufferHandler()` 及其助手）**：①新增 `UartRecvFrameReady()`，按长度域算整帧长度，没收齐就退回等数据且 `readIndex` 不动；②收齐后直接进 `PARSE_DATA` 并按整帧长度推进 `readIndex`（顺带堵掉"数据域含 `AA 55` 会提前截断"的隐患）；③`u16WriteIndex` 加取模，避免收满缓冲时等于 256 导致状态机死锁。

  - 根因：**W5500 UDP 模式的接收缓冲每条数据报前面有 8 字节报文头**（源 IP 4 + 源端口 2 + 负载长度 2），且 `Sn_RX_RSR` 把这 8 字节算在内。驱动原 `W5500_SocketRecvFrom()` 是"调 TCP 的 `W5500_SocketRecv()` 再读 `Sn_DIPR`"的简化实现，把报文头当成负载返回，`DiscoveryRequestValid` 首字节是源 IP 不是 `0x55`，永远校验失败 → 静默丢弃 → 不复包。官方 ioLibrary `recvfrom()` 正是"先读 8 字节头再读负载"。
  - 修复（`W5500_SocketRecvFrom` 重写）：读 `Sn_RX_RSR` < 8 返回 0 → 从 `Sn_RX_RD` 处读 8 字节头 → 解析源 IP/源端口/负载长度 → 按 `min(负载长度, 用户缓冲)` 读负载（起点 `offset+8`，走回卷处理）→ **`Sn_RX_RD` 推进 `8 + 整条负载长度`**（截断时剩余部分也必须消费，否则读指针与芯片失步）→ 发 `RECV`。源地址直接用报文头，不再读 `Sn_DIPR`（该寄存器会被后续数据报覆盖）。
  - 两工程同源已同步（`F103_W5500/W5500/W5500.c` 与 `FlexControlSTM32/Application/W5500.c` 现在逐字节一致，除本函数外原本也无差异）。编译：FlexControl 0E0W（Code 31710）、F103_W5500 0E0W（Code 10396）。
  - 附带排查工具：`doc/udp_discovery_test.py`（不依赖 Qt，可单播指定 IP + 自动按网卡算定向广播），能区分"设备不回"与"Qt 被防火墙拦"。
